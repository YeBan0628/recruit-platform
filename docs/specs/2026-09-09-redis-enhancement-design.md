# Redis 增强现有职位与投递链路设计

## 1. 目标与范围

本阶段在现有职位、投递服务基础上引入 Redis 能力，目标是提升职位读取性能、提供职位热度榜，并降低并发重复投递风险。

本阶段包含：

- 职位详情缓存
- 职位详情缓存失效
- 职位热度 ZSet 与热度榜查询
- 投递幂等短锁

本阶段不包含：

- Redis Stream、分布式事务、缓存框架二次封装
- 职位分页结果缓存
- 附近职位 Geo
- 热度定时衰减

## 2. 现状与约束

- Redis 地址、密码从各服务的 `application-local.yml` 读取。
- position-service 使用 MyBatis-Plus 查询职位，delivery-service 负责投递落库。
- 数据库唯一约束仍是重复投递的最终兜底，Redis 不是唯一一致性来源。
- 现有接口路径保持兼容，不改变已有请求和响应字段。

## 3. 方案

### 3.1 职位详情缓存

- position-service 查询职位详情时先读取 `position:detail:{id}`。
- 缓存值使用 JSON 序列化的 `PositionDTO`，TTL 30 分钟。
- 仅缓存可正常返回的职位详情；不存在或已删除的职位不写缓存。
- 发布、修改、上下架、删除成功后删除对应详情缓存。
- Redis 不可用时降级为直接查询数据库，不影响主流程。

### 3.2 职位热度

- 使用 ZSet：`position:hot:score`。
- 查询职位详情成功后增加 1 分浏览热度。
- 投递成功后增加 5 分投递热度。
- 新增接口 `GET /position/position/hot?limit=10`，按分数倒序返回职位详情列表。
- 热度榜只返回数据库中仍存在且状态正常的职位；无效成员在读取时清理。
- 热度统计失败不影响职位查询或投递主流程。

### 3.3 投递幂等短锁

- delivery-service 在写入投递记录前尝试获取 `delivery:lock:{applicantId}:{positionId}`。
- 使用 Redis `SET NX EX` 语义，锁 TTL 10 秒。
- 获取不到锁时返回“请勿重复提交”业务错误。
- 数据库唯一约束继续负责最终防重；数据库失败或成功后都释放锁，锁只用于覆盖并发写入窗口，避免阻塞用户后续合法操作。
- Redis 不可用时回退到数据库唯一约束，不让缓存故障阻断投递。

## 4. 数据流

### 职位详情

请求 → position-service → Redis 详情缓存 →（未命中）MySQL → 写入缓存 → 增加热度 → 返回。

### 投递

请求 → 获取 Redis 幂等锁 → 校验职位与用户 → MySQL 写入 → 增加职位热度 → 发布 RocketMQ 事件 → 释放/过期锁 → 返回。

## 5. 错误处理

- Redis 连接、序列化、读写异常统一记录日志并降级，不向用户暴露基础设施细节。
- 缓存解析失败时删除坏缓存并回源数据库。
- 热度榜查询遇到单个失效职位时跳过该职位并清理 ZSet 成员。
- 重复投递同时存在 Redis 锁和数据库唯一键两种情况时，统一返回同一业务错误语义。

## 6. 测试与验收

- 单元测试覆盖缓存命中、缓存未命中回源、写操作失效缓存。
- 单元测试覆盖热度加分和榜单排序。
- 单元测试覆盖幂等锁获取成功、获取失败、Redis 异常降级。
- 手动验证：详情首次访问与再次访问、修改后缓存失效、热度榜、重复投递、RocketMQ 通知链路。
- Maven 全量编译通过。

## 7. 兼容与回滚

- 不修改已有数据库表结构。
- 删除新增 Redis key 即可清空缓存和热度数据，不影响 MySQL 主数据。
- 回滚代码后，服务仍可直接使用数据库完成职位查询和投递防重。
